# CLAUDE.md

Instructions for Claude Code working on CovDecayAnalyzer. Keep this file
short. Long-form context lives in `NOTES.md` and `vignettes/`.

## What this project is

CovDecayAnalyzer is an R package for analyzing sequencing coverage decay
around a user-supplied anchor position on a linear reference genome. Primary
user flow, scope boundaries, and methodological commitments are documented in
`NOTES.md`. Read it at the start of every session.

The package is used by the Goodrum/Bosco lab at Dartmouth for HCMV genomics,
but nothing in the methods is HCMV-specific. The intended release path is
GitHub public followed by Bioconductor submission.

Carly Bobak owns the methods, the package scope, and the commit history.

## How to work here

Work directly in the main branch working tree. Do not create git commits, do
not create branches, do not push. Carly reviews uncommitted changes with
`git status` and `git diff`, and commits herself. The only exception is a
task that spans multiple working sessions and cannot be committed as a
single coherent change; in that case, create a feature branch and tell Carly
in your response.

Write freely in `R/`, `tests/`, `vignettes/`, `simulations/`, `inst/`, and
`NOTES.md`. Read anywhere.

Do not modify `DESCRIPTION`, `NAMESPACE`, or `CLAUDE.md` without an explicit
instruction. `NAMESPACE` is generated by `devtools::document()`; if the
NAMESPACE needs to change, modify the roxygen headers in `R/` and run
`document()`.

Run `devtools::test()` and `devtools::check()` freely. Capture their output
to files when the result matters for the task. `covr::package_coverage()` is
useful before and after any change to confirm coverage did not drop.

Do not run `install.packages()` without checking first. The package's
imports are pinned by `DESCRIPTION`; adding a new dependency is a design
decision, not a convenience.

## Do not touch without permission

The following files encode methodological commitments. Do not modify them
without explicit instruction from Carly. You are expected to critique them
in writing when working nearby, and to propose specific alternatives where
you see a better approach. "I think X is wrong because Y, and here is what Z
would look like instead" is useful. "I think X is wrong" is not.

- `R/decay_tests.R`
- `R/null_distribution.R`
- The methodological sections of `vignettes/null-distribution.Rmd`
- The methodological commitments in `NOTES.md`
- Any git history before the `baseline-pre-claude` tag

Surface critiques in your response to Carly, not silently in a code comment
she will not read.

## How to disagree

Three categories, split by scope rather than severity:

Stylistic or implementation disagreements (naming, code organization, which
helper to use). Proceed with Carly's instruction. Add a one-line note in
your response explaining the alternative. Do not stop.

Factual disagreements (Carly's assertion appears incorrect, or a stated
fact contradicts what the code or docs show). Stop and ask one targeted
question. Do not proceed on either interpretation until she answers.

Methodological or statistical disagreements (changes to test machinery,
p-value formulas, assumptions, package scope). Stop and write a short memo
(half a page or less) with the concern, a specific proposed alternative,
and the implications. Nothing proceeds until Carly replies.

## Session start

Before any file changes, every session:

1. Read `NOTES.md` for current state and punch list.
2. Run `git log --oneline -5` to see recent commits.
3. Run `git status` to see any uncommitted work in progress.
4. Confirm the task you were given still makes sense given 1 to 3. If not,
   ask before proceeding.

## Code conventions

- Match the indentation and brace style of surrounding code. Do not
  reformat untouched regions.
- Use `@importFrom` roxygen tags for imported functions; do not use
  `pkg::function` prefixes inside package source. In vignettes and examples,
  use `pkg::function` for clarity.
- Every exported function has runnable `@examples` and a `@return` tag
  describing the return value's class and structure.
- Test files live at `tests/testthat/test-<file>.R` matching
  `R/<file>.R` naming.
- Package tests verify what the package claims. The simulation study in
  `simulations/` verifies that what the package claims is scientifically
  reasonable. Keep the two separate.

## Visualization

Use colorblind-friendly palettes in every plot, including quick diagnostic
plots in test outputs and simulation code. Default to Okabe-Ito for
categorical data and viridis for continuous. Avoid red-green combinations.

## When in doubt

Ask one targeted question. The marginal cost of a question is low; the
marginal cost of silent drift from the project's intentions is high.
